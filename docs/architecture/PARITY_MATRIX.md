# Parity: what proves the game is unchanged

Stage 3H's rule: **the engine may change, the experience may not.** This page says, for each part of the experience, which machine
check shows it is unchanged, and what no machine check here can judge. The second list is Human QA's.

The references are the accepted B++ head `143b63ff42b88c6780c5043e0f61d64100f81f40` and the frozen Stage 3H2 `22751bbc39c91f3e54e3305638b2ef2c9dd12c68`.
Every step that compares behaviour (the traces, the protocol, the mutants, HTTP, the live wire, the browsers, the pixels, the suites,
performance) compares against B++, never against the previous checkpoint. Byte identity is checked against 3H2, except where the
continuation retired it on purpose: for code made of modules (the server's sim since C3a, the page's `world.js`, `move.js`,
`camcorder.js`, `glitch.js` and `ents.js` since C3b, and `mp.js` since C3c) and for the compiled client built from its TypeScript
(since C4b; Level 0's definition since C4c). Their behaviour is compared with B++'s instead. Since C5,
M8 (`c34f0c22bbacc5ac2813d173bc0591b67af7169f`), the gameplay-parity reference, is a direct reference too: every comparison that can
take M8 as its old side was run against it, and all pass: every trace, result, response, frame, check and pixel equal, the time
within its rule (`c5_vs_m8.js`, below).

## Two facts carry most of the weight

1. **The browser gets the same bytes, or the same behaviour.**
   - 40 of the 48 files under `public/` are byte-identical to the frozen 3H2's file at the same URL. So are two of the server's three
     built files (`ai.js`, `dphys.js`) (`node dev/stage-3h-modernization/tools/m8_served_identity.js`).
   - Five are the scripts C3b made of modules: `world.js` (and the server's copy, the same bytes), `move.js`, `camcorder.js`,
     `glitch.js`, `ents.js`. Each line is M8's, inside its owner's factory, except the edits `c3_client_modules.js` lists (three
     couplings across owners made explicit). The gate's `page` step runs B++'s script and this one side by side: `world.js`'s every
     function in Node, the other four in the same closed Chromium page, every trace equal, each scene reaching its script.
   - The sixth is `mp.js`, made of modules at C3c: 863 of M8's 921 lines are as they were, every other line listed with its reason
     (`c3c_mp_provenance.js`: each owner's state its own, a write of it a call of the owner's function, a read a call of its reader,
     the session's late wiring). The gate's `cli_golden` step runs all 18 client scenes on B++'s `mp.js` and this one in the same closed
     page, every trace equal byte for byte, and together they run every one of its functions.
   - Four files differ from B++'s because of 3H2: it moved code out of `mp.js` into `assets/net-newrun.js` and `assets/mp-hum.js`,
     and `index.html` loads them. The page traces, the page mutants and the real-browser checks below cover that change.
   - Two are the compiled client, built from its TypeScript since continuation C4b: `assets/index-DKbV5Nv9.js` and
     `assets/index-D7hdwmUU.css`. The port is the shipped program, statement by statement (the gate's `port` step), and the built
     client and B++'s recorded one do the same in the page, frame by frame, in nine scenes (`bundle`). Since C4c the bundle is built
     with the one definition of Level 0 and the lights; it differs from C4b's in one token (the lantern's spread, the same double).
   - Everything else is B++'s own bytes: the PixiJS chunks, the images and the sounds.
2. **The server gives the same answers.**
   - The world it runs: `ai.js` and `dphys.js` are 3H2's bytes; `world.js` is the page's module script (C3b). The sim is modules
     since C3a: each line is M8's, moved, except the edits `c3_sim_modules.py` lists (a write into another owner's state became a call
     to that owner's function). The gate's `sim` step gives it, with this tree's `world.js`, and B++'s `sim.js`, with B++'s, the same
     20,050 calls: every result equal. Since C4c its level reads the one definition of Level 0 (`level0.json`, `lights.json`);
     `c4c_level0_check.js` builds the level before and after and compares everything it gives the sim (198,648 comparisons).
   - `server.js` was split into modules with every moved line verbatim (the M2 move proof).
   - In 18 scripted scenarios, B++'s `server.js` and this one, run on the same files, send the same bytes. Both equal B++'s stored
     traces, except for 18 lines of `http_base`: the responses that carry the served files changed on purpose (3H2's `index.html` and
     `mp.js`, which C3c changed again; C3b's five module scripts; since C4b the compiled client's bundle and stylesheet). Those
     responses' bodies are checked against the files themselves.

So for players, the code can only behave differently through what the server sends and when: those are the traces and the
performance step. Or it can differ through what no check here reaches: a real network, other browsers, phones, ears and eyes.

## Inherited, pinned, not fixed

The rule forbids fixing inherited bugs during modernization, so these stay as they are on B++. The gate checks that they stay that
way:
- **Suites that fail on B++ too.** The gate checks that only those cases fail: `npm test` 13, `s_humanqa_hotfix` X03, `test_shadows`
  5, `test_br_role` 3, `audit_net` 4, `audit_net2` 3.
- **The two caveats in B++'s report** (findings F-019 and F-020), pinned byte for byte by `bpp_known_limits`:
  - an admin's own GOTO followed by stale poses;
  - a BRING whose stale pose arrives after the grace.
- **`place_replay.js` can fail one case by chance** (F-036).
- **`perf` can fail by chance on a small machine** (M-021). The gate's README says how to tell noise from a slowdown.
- **`gameplay_smoke` (the `browsers` step) can fail by chance:** the real server picks a random world, and a monster can kill a
  player before the check's admin connection removes the monsters (seen on C3a's, C3b's, C4c's and C5d's full gates; then 10 of 10 runs
  OK on C3a and C2 alike, and 10 of 10 alternating C3b and C3a). `dev/stage-3h-modernization/tools/c3a_early_death_check.js` shows
  B++'s sim and this one give the same deaths in 150 worlds. Since C3b the gate runs the check once more when that happens, and says
  so. The same check's walk after SPAWN can also meet a wall: the spawn spot is random, and Alice walks south from it (seen once, in a
  re-run of C3b's browsers step: the spot (4488, 5832) has a wall 20 px to its south, which the sim's `moveOk` confirms). The step
  passed when run again.
- **The contact lab's `peers_visible` image can differ by one level in a few pixels** (the `contact_lab` step; M-036): BR-RoLE eases
  a light's weight on a body a fixed share a frame, and the lab captures after a wait in real time, so the other player's cast is a
  hair further along in one run than in another, on B++ as on this tree. Seen once, in C4c's full gate (133 pixels, each by 1); the
  step passed when run again. The gate still compares every pixel.
- **`two_browser.py` (the `browsers` step) fails when the watching page's frames are long** (M-037): it samples the other player's
  avatar inside BR-RoLE's draw, before `mp.js`'s hook moves it to the drawn pose, and `mp.js` moves the drawn pose between frames
  when a newer pose is more than 96 px away, which a sprint reaches only when frames are long. Seen once, in C5d's final gate, while
  a build ran beside it (3 of 79 frames); the step passed when run again alone. With the watching page alone slowed by Chromium's
  CPU throttling, M8's game fails it the same way as this tree's (`evidence/c5d/browsers_diagnosis/`).
- **The carpet texture is the HAR recovery's placeholder** (M-013).
