# dev/tools: the lasting development tools

Development only. Nothing here is served or loaded by the game. Zero dependencies unless a line says otherwise.

| Tool | What it does | Command |
|---|---|---|
| `build/build.js` | Builds every output in `src/build-recipes.json` into `public/` (served) and `generated/server/` (loaded by the server), and records every hash in `generated/BUILD_MANIFEST.json`. An output is its parts, concatenated (the PixiJS chunks: copies of the recovered v11 build output), or (since continuation C4b, the compiled client's bundle and stylesheet) the record of the client build: `build.js` does not build them, it checks that their sources and inputs are the ones `generated/CLIENT_BUILD.json` lists and the files the outputs it lists (until C4a they were a replay of the client lineage). `--check` fails when a committed output is not what `src/` builds | `npm run build`, `npm run build:check` |
| `layout.js` | Where the game's files are. Tests and tools ask it for a runtime file by its old root name (`mp.js`, `sim.js`, `server/ws.js`, `dev/ents_src/10_hound.js`) instead of hard-coding a path, so they work on this layout and on an old-layout tree (a B++ or Stage 3H2 export). `runtimeOf` lists a tree's runtime by old names (a server module made after the modernization, by its own path); `projectOld` writes it out as an old-layout folder; `serverSource()` is the server's own code as one text (`server.js` and the modules split out of it). Also a command line, for other languages: `node dev/tools/layout.js at sim.js` Since continuation C3a, `sim.js` names the sim's composition (`src/core/server/sim.js`), and `simFiles()` / `simSource()` (`node dev/tools/layout.js sim-files`) give every file of the sim, for the tests that read its code; `projectOld` points the composition's requires at the copied files. | — |
| `checks/parts.js` | The parts checker. Each part of a built output begins with a `/** @part ... */` header (removed by the build) that lists what it provides to the other parts of its script, what it uses of theirs and which of their bindings it writes. The checker finds the shared closure with TypeScript, gives each statement to its part (a split must fall between statements), and fails on any header that does not match the code. `--suggest <output>` prints the lists for a new part; `--fix <output>` rewrites them after an edit. **Needs TypeScript** (the package, Node's global copy, or `$TYPESCRIPT`) | `node dev/tools/checks/parts.js` |
| `checks/modules.js` | The module-boundary audit (continuation C3; needs TypeScript, like the parts checker). For server.js and every server module: every name it uses is its own, given to its factory, or the host's or the language's; it never reaches the global object; a factory never assigns a name it was given and uses every one. For the sim: no state outside a module's factory, and the composition makes each module from modules made before it, importing only names its giver returns. For the page's module scripts (continuation C3b: `world.js`, `move.js`, `camcorder.js`, `glitch.js`, `ents.js`; C3c: `mp.js`), as the build assembles them: only the factories and the composition in the script's wrapper; a factory uses its own names, what it is given and the page's globals; the composition's order and wiring; the headers' `imports`, `exports` and `late` names; no write into another owner's state, nor change of it in place, except through that owner's function; one module per entry of a public object (`W`, `E`, `mv`, `N`); no call of a function a third module put on another's object; no global back-channel inside a script; one module per name on the global object and per thing written through it; a module given later modules (`mp.js`'s session) gets them only through its `wire`, called once after the last module is made, and uses none while it is made. `--dir` checks another copy of the game | `node dev/tools/checks/modules.js [--out FILE.json]` |
| `checks/window_contract.js` | The compiled client's side of the page's window contracts (continuation C4d; needs TypeScript, like the parts checker). Every window member the client's TypeScript reads or writes is declared in `src/core/client/game/client/contracts.d.ts` and every declaration used; window is never cast to escape them; no member the client reads is left undefined by the page's scripts; every script that writes a member is named in its declaration; the built bundle reaches the same window names as its source. `--mutants 1` shows each rule refusing a break | `node dev/tools/checks/window_contract.js` |
| `checks/facts.js`, `checks/facts.json` | The facts the runtime writes in more than one place (continuation C4d; zero dependencies). `facts.json` lists each fact, its value and every copy (a file and a pattern, or a path into a `.json` file); the check fails unless every copy is found where it is listed and holds the value (FINDINGS M-028). `--mutants 1` changes each copy alone and shows it caught | `node dev/tools/checks/facts.js` |
| `checks/dev_workflow.js` | A developer's round trip, checked (continuation C5; the gate's full-tier `workflow` step; needs Playwright's Chromium). On a scratch copy of what plays and builds (the working tree as it is on disk, or `--ref COMMIT`): the build check; a page module edited, `build.js --check` refusing it, `build.js` writing `public/mp.js` and the manifest only, the copy's own server serving it and a real page showing it; a server module edited (not built), the restarted server answering with it; both undone and every output byte for byte as before; `build.js --clean` and a clean rebuild, byte for byte; with `--packages <folder>` (since C4b) the compiled client's round trip too: a TypeScript edit refused by `build.js --check`, built by `client.js`, served and seen through `window.__api`, undone and rebuilt byte for byte |
| `checks/chat_browser.js` | The chats in real pages (post-3H Trial 2; needs Playwright's Chromium): one server, several headless pages through the boot gate; the lounge (across rooms, typing isolated from the game and menu, markup literal, mute, fold, off, the phone's Lounge button, closed during a run, its place at five sizes) and nearby speech (the composer, bubbles, the edge hint pointing the right way, nothing beyond the radius or in another room, hide, mute, a leaver, SAY on a phone, reduced motion). `--mutants 1`: seven faults in a copy of the page's chat.js, all to be caught; `--shots DIR` |
| `checks/rgb_browser.js` | Trial 4's RGB sliders in real pages (post-Trial 4 review; needs Playwright's Chromium): one server, a desktop and a phone page with known saved colours; the sliders follow the saved colour, swatches and Reset HUD, move one channel from the keyboard, fit their boxes; `--mutants 1` (6 mutants). The gate's full-tier `rgb` step. |
| `checks/chat_server.js` | The chat's server side (post-3H Trial 2; `docs/architecture/CHAT.md`): W.A.R.D.'s text check, B++'s `speech.js` on hand-made rooms and `lounge.js` on fake sockets, then the real server driven by raw WebSocket clients (nearby speech by radius, room, life and spoofed fields; the lounge across rooms, its handshake, Origin, limits and caps; no line crossing between the two; the game's snapshot pace under lounge load; no text in the server's output). `--mutants 1`: 13 copies of the server with one deliberate fault each, all to be caught. No browser needed; about 5 minutes with mutants |
| `checks/menu_drift.js` | The main menu's title drift (post-3H Trial 1; the gate's full-tier `menu` step; needs Playwright's Chromium). On two game folders, the accepted C5d and the candidate, each served by its own server with a synthetic passcode: the candidate's title moves with no pointer, within 3 px an axis and without a jump; a hidden tab, reduced motion (Settings On, the device's under System, at boot and while running) and a run stop it, with no frame asked for and nothing written; it resumes with one loop; the pointer's lean is C5d's. At four sizes the menu's controls, text, Tab order and title at rest are C5d's; the logo, `index.html`, the music's state and the sound button too. `--mutants 1`: eight edits of the change, each caught | `node dev/tools/checks/menu_drift.js --old-dir <C5d game> --new-dir <candidate game> [--mutants 1] [--shots DIR]` |
| `build/client.js`, `build/packages.js` | The compiled client's build (continuation C4; needs npm and the 31 locked packages of its lockfile, `TFB_V11_LINUX_X64_PACKAGES.zip`, never committed). `packages.js` checks a folder of tarballs against the lockfile (each one's SHA-512, by the package.json inside it); `client.js` installs them offline into a scratch folder and builds `src/core/client/game/` with its own `npm run build` (TypeScript, Vite): `--stage` into a scratch folder, `--check` against the served files and the record, `--write` into `public/assets/` with the record `generated/CLIENT_BUILD.json`. `--record-check` needs no packages: the record against the tree and the served files | `node dev/tools/build/client.js --packages <folder> --stage <scratch>`, `--record-check` |
| `lineage/recorded.js` | The compiled client as the lineage records it (continuation C4b): the bundle or the stylesheet B++ shipped, replayed from the ledger with every step's SHA-256 checked, for the tests that read B++'s minified text (FINDINGS M-033) | `require('./dev/tools/lineage/recorded.js').recorded('bundle')` | `node dev/tools/checks/dev_workflow.js [--ref COMMIT] [--out F.json]` |
| `docs/docs.js` | The documentation's generated tables: every built output and its sources (`docs/architecture/BUILD_PIPELINE.md`), every framework and what its files go into (`FRAMEWORKS.md`), each framework's files (its `README.md`), and every `window.__name` the served scripts write or read (`CONTRACTS.md`). Each table sits between two markers; the text around it is written by hand. `--check` fails when a table is not what the repository gives today, or a document lacks its table, holds it twice or holds another's (the gate's `docs` step) | `node dev/tools/docs/docs.js` (rewrite), `--check` |
| `gate/` | The gate: the working tree against the accepted B++ game, deterministic and live. See `gate/README.md` | `npm run gate`, `npm run gate:full` |
| `lineage/lineage.js` | The client lineage ledger: `verify` replays how each file of the original v11 build became the shipped file, checking every step's hashes and `blame.json`; `tree-id` proves `src/core/client/bundle/original-v11/` is the recovered snapshot; `record` turned a change to the bundle or its stylesheet into the next step until continuation C4a, and refuses the two chains since C4b (they are history: the files are built from `src/core/client/game/`); `show` prints a step; `blame` prints who wrote the shipped bundle's bytes. See `src/core/client/bundle/README.md` | `node dev/tools/lineage/lineage.js verify` |

Stage-specific tools stay in their stage's folder, for example `dev/stage-3h-modernization/tools/`. The tools of earlier stages are
kept as they were, for their own layout: `dev/stage-3h0/`, `dev/stage-3h/` and the rest.
